# Лаборатори 3 — Чанарын сценарио ба SLO

**Д.Бүрэнтөгс · B222270092**

| Системийн төлөв | API хэвийн ажиллаж байгаа | Төлбөрийн үйлчилгээ ажиллаж байгаа | API хүсэлт авч байх үед процесс унана | Тайлангийн зам ажиллаж байгаа |

## SLO ба төсөв

| Сценарио | SLI | Босго | Цонх |
|---|---|---|---|
| Гүйцэтгэл | Сагсны хүсэлтийн хугацаа | p95 < 20 мс | 1 мин, 20 VU |
| Найдвартай байдал | Төлбөрийн алдааны хувь | < 7.5% | 1 мин, 20 VU |
| Бэлэн байдал | Бүх HTTP 200 шалгалтын хувь | ≥ 90% | 2 мин, 20 VU, 10 с зогсолт |
| Сэргэлт | Процесс зогссоноос эхний амжилттай probe хүртэлх хугацаа | ≤ 15 с | Chaos туршилт, тусдаа хэмжилт |
| Тайлан | Тайлангийн хүсэлтийн хугацаа | p95 < 430 мс | 1 мин, 20 VU |

Сагсанд зориудын хүлээлт байхгүй тул локал орчинд 20 мс-ийн хязгаар тавив. Төлбөрийн загварчилсан 5%-ийн алдаанд 2.5 нэгж хувийн зай үлдээв. Тайлангийн дээд хүлээлт 400 мс тул 430 мс нь нэмэлт боловсруулалтад 30 мс үлдээнэ. Бэлэн байдлын 90%-ийн зорилт нь 120 секундэд 12 секундын хугацааны төсөвтэй. Сэргэлтийн 15 секундийн хязгаар нь төлөвлөсөн зогсолт дээр дахин асахад 5 секунд нэмнэ.

## Ажиллуулах

```text
k6.exe v2.4.0 (commit/dd9395906d, go1.26.11, windows/amd64)
```

Эхний терминалд `node server.js` ажиллуулна. API зөвхөн локал 3203 порт дээр ажиллана. Хоёр дахь терминалд:

```powershell
New-Item -ItemType Directory -Force results | Out-Null
k6 run --no-color --quiet slo-test.js 2>&1 | Tee-Object results/pass.txt
k6 run --no-color --quiet -e MODE=chaos slo-test.js 2>&1 | Tee-Object results/chaos.txt
k6 run --no-color --quiet slo-test-fail.js 2>&1 | Tee-Object results/fail.txt
$LASTEXITCODE
```

Chaos гүйлт эхэлснээс ойролцоогоор 40 секундийн дараа серверийг зогсоож, 10 секунд хүлээгээд дахин асаана. Сагсны зам HTTP 200 буцаах хүртэлх хугацааг тусад нь хэмжинэ.

## Хэмжилтийн үр дүн

| Гүйлт | Сагсны p95 | Тайлангийн p95 | Төлбөрийн алдаа | Нийт HTTP алдаа | Амжилттай шалгалт | Гарах код |
|---|---:|---:|---:|---:|---:|---:|
| [pass](results/pass.txt) | 644.51µs | 397.09ms | 4.97% | 1.65% | 98.34% | 0 |
| [chaos](results/chaos.txt) | 638.56µs | 397.4ms | 15.30% | 12.27% | 87.72% | 99 |
| [fail](results/fail.txt) | 643.41µs | 397.51ms | 4.96% | 1.65% | 98.34% | 99 |

Хэвийн ачаалалд 20 VU нийт секундэд 45.238677 хүсэлт илгээсэн.
Chaos үед хүсэлтэд суурилсан бэлэн байдал 4987 / 5685 = 87.72% байв. Нийт алдаа 698, зөвшөөрөх дээд хэмжээ 568 учраас хүсэлтийн төсөв хэтэрсэн.
Зогсолтоос амжилттай probe хүртэл 11.35 секунд хэмжигдэж, 12 секундын хугацааны төсөвт багтсан. [Сэргэлтийн хэмжилт](results/recovery.txt).
Chaos үед бэлэн байдал FAIL, төлбөрийн найдвартай байдал FAIL болсон. Холболт татгалзах үед тайлангийн 200–400 мс хүлээлт алга болж, нэгж хугацаанд илүү олон хүсэлт алдах боломжтой. Төлбөрийн загварчилсан алдаа ч хүсэлтийн төсвөөс зарцуулна.
Зориудын FAIL гүйлтэд `http_req_duration{name:report}` мөрийн `p(95)<100` шалгуур унаж, k6 99 код буцаасан.

## Дүгнэлт

Сценариог SLO болгоход хамгийн хэцүү нь бэлэн байдлыг хугацаагаар уу, хүсэлтээр үү гэдгийг тодорхойлох байв. Сагсны p95-ийг өөрийн tag-аар хэмжихэд тайлангийн зориудын саатал түүнд нөлөөлөөгүй. Хэвийн гүйлт бүх босгыг давсан. Chaos туршилтаар API 11.35 секундэд сэргэж, сэргэлтийн шаардлагыг хангасан. Хүсэлтээр хэмжсэн бэлэн байдлын шалгуур FAIL болсон. Хугацааны төсөв болон хүсэлтийн төсөв өөр өөр үр дүн өгч болно, учир нь хүсэлтүүд зогсолтын үед ч үргэлжилнэ. Төлбөрийн SLI-г зөвхөн API ажиллаж байх үеийн төлбөрийн хариугаар, бэлэн байдлыг тусдаа probe-оор хэмжвэл хоёр шалтгааныг ялгаж болно. Тайлангийн 100 мс босго зориуд унаж, k6-ийн гарах код CI шалгалтыг зогсоох боломжтойг харуулав.
